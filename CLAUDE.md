# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Ksinito is a real-time multiplayer online casino (European roulette + blackjack, a single-player trivia game with a stake, plus a free single-player duck-shooting minigame that earns credits) using play-money credits. Node.js + Express 5 + Socket.IO + MySQL (`mysql2/promise`) on the server; on the client, Bootstrap 5 (CSS + JS bundle) with plain JS modules and no build step. All user-facing text, code comments and error messages are in **Spanish** — keep it that way.

## Commands

```bash
npm install
cp .env.example .env   # set DATABASE_URL
npm start      # http://localhost:3000
npm run dev    # same, with node --watch auto-restart
```

- Requires Node.js >= 22.9 (the scripts use `--env-file-if-exists=.env`) and a reachable MySQL 8.0+ (or compatible: TiDB, PlanetScale, Aiven). Startup (`main()` in `server.js`) retries the connection for ~1 min, applies `db/schema.sql`, then loads the JWT secret and avatar versions before listening.
- `npm test` runs `node --test` (built-in runner, no deps) over `test/`: the duck trajectory (`duck-path.test.mjs`), `DuckRound` shot validation (`ducks.test.js`), ranks (`ranks.test.js`) and `TriviaRound`/payouts/question bank (`trivia.test.js`), all without a DB. There is no linter or build step. `socket.io-client` is a devDependency for ad-hoc scripted clients (connect with the `ksjwt` cookie from `/api/register` or `/api/login`).
- Env vars: `DATABASE_URL` (or `MYSQL_HOST/PORT/USER/PASSWORD/DATABASE`), `DATABASE_SSL=1` (TLS, required by most hosted MySQL), `DATABASE_POOL_SIZE`, `JWT_SECRET` (≥32 chars; if unset one is generated and stored in the `settings` table), `PORT`, `COOKIE_SECURE=1` (HTTPS), `TRUST_PROXY`, and the rewarded-ads settings `ADS_ENABLED`, `AD_REWARD`, `AD_DURATION_SECONDS`, `AD_COOLDOWN_SECONDS`, `AD_DAILY_LIMIT`, `AD_CLAIM_WINDOW_SECONDS` (validated at startup in `ads.js`; invalid values fall back to the default with a warning), and the duck-game settings `DUCKS_ENABLED`, `DUCK_REWARD`, `DUCKS_PER_ROUND`, `DUCKS_DAILY_CREDIT_LIMIT`, `DUCKS_ROUND_COOLDOWN_SECONDS` (validated the same way with `intEnv()` from `src/env.js`). `GET /api/health` pings MySQL.
- The app must run as a single long-lived Node process: game state, timers and Socket.IO rooms live in memory, and avatar versions are cached in memory. It can't run on serverless platforms (Vercel, Netlify), and it isn't safe to run several instances.

## Architecture

### Security model: server-authoritative credits
The core invariant: **the client only sends intents; the server validates everything and is the only thing that can create credits.** Preserve this when changing anything.

- `src/wallet.js` is the **only** module that mutates `users.credits`. Every change goes through `debit`/`credit`/`bet`/`refundBet`/`grantWelcomeBonus`/`transfer` (all async), which run in a MySQL transaction and write rows to the `ledger` table (reason strings like `roulette:bet:<key>`, `blackjack:double`, `transfer:out:<id>`, `ad_reward:<id>`, `duck_reward:<roundId>`). `credit(userId, amount, reason, tx)`, `bet(…, tx)` and `refundBet(…, tx)` can run inside a caller's `db.transaction()`; their `'balance'`/`'wagered'` events are then deferred with `tx.onCommit`. `debit` returns `null` on insufficient funds (the SQL `WHERE credits >= ?` guard + `CHECK (credits >= 0)`), which games translate into a `GameError`. `transfer` locks both user rows in id order (`SELECT … FOR UPDATE`) to avoid deadlocks, and retries once on `ER_LOCK_DEADLOCK`. Invariant to keep: for every user, `SUM(ledger.delta) = users.credits`. Game stakes must use `bet()`, and refunds of stakes that were never played must use `refundBet()`, never `debit()`/`credit()`: they also move `users.wagered` (the rank) and emit `'wagered'`. Payouts stay `credit()`.
- Never add an HTTP endpoint or socket event that adds credits. Credits only enter via the one-time welcome bonus (guarded by `welcome_bonus_granted`), game payouts computed server-side, `POST /api/ads/claim` (validated entirely server-side, see `ads.js`), or the free duck game's end-of-round payout (hits decided server-side, capped per day, see `ducks.js`); transfers only move them.

### Concurrency: every game mutation goes through a queue
MySQL calls are async, so a game could change state while a debit is pending (limits checked twice, phase changing mid-bet). Each `RouletteGame` and `BlackjackTable` owns a `SerialQueue` (`src/queue.js`). Public entry points (`placeBet`, `clearBets`, `sit`, `leave`, `act`) are wrappers that `queue.run()` a private `#method`, and timers call `queue.fire()`. Internal methods call each other directly — never call `queue.run()` from inside a queued operation, or it deadlocks. `BlackjackTable.schedule()` stamps each timer with `timerGen`, so a timer that was already queued when a newer one replaced it does nothing. `server.js` has a separate `seating` queue so one user can't sit at two tables from two tabs.
- Randomness uses `crypto.randomInt`. The dealer's hole card is replaced by `null` in `BlackjackTable.publicState()` until revealed — never send hidden state to clients.
- `wallet.events` emits `'balance'`; `server.js` forwards it to the `user:<id>` room so all tabs of a user update.

### Server (`src/`)
- `server.js` — wires Express (security headers/CSP, `/api` auth router, static `public/`) and Socket.IO (same-origin check, cookie-based socket auth). All game socket events are registered via the local `on(event, handler)` wrapper, which applies a per-socket token-bucket rate limit and converts exceptions into acks `{ ok, error }`. Only `GameError` messages are shown to players; any other error is logged and returned as `'Error interno'`. Also manages the 20 s grace period before a disconnected user loses their blackjack seat (counted across multiple tabs).
- `errors.js` — `GameError` (player-safe message, plus optional `extra` data that `on()` spreads into the ack, e.g. `retryAfter`) and `assertInt` for validating client payload numbers.
- `auth.js` — register/login/logout/me under `/api`. Sessions are stateless HS256 JWTs (`jsonwebtoken`) in the httpOnly cookie `ksjwt`, 7-day TTL, re-issued by `/api/me` once older than a day. `verifyToken` also loads the user and requires the `ca` claim to equal `users.created_at`, so a token can't authenticate as a different account that reused the same id after a DB wipe. Logout only clears the cookie; there is no server-side revocation. Welcome bonus is granted in `loginResponse`. In-memory per-IP rate limiting.
- `avatars.js` + `profile.js` — profile photos (`avatars.init()` preloads every avatar version so `avatarUrl()` stays synchronous). `PUT /api/avatar` takes the raw image body (the client has already cropped it to 256×256 WebP/JPEG). `avatars.imageInfo` checks the format from magic bytes (JPEG/PNG/WebP only) and parses the dimensions from the headers, capping them at 1024 px so other players' browsers can't be made to decode huge images. Photos are BLOBs in the `avatars` table. `GET /api/avatar/:id?v=<updated_at>` is public and immutable-cached. `avatarUrl()` caches versions in memory because `BlackjackTable.publicState()` calls it on every broadcast. `avatars.events` `'change'` makes `server.js` emit `profile` to the user's tabs and re-broadcast the table if they're seated.
- `db.js` — `mysql2/promise` pool and helpers: `query(sql, params)` (rows, or `{affectedRows, insertId}`), `one()`, `transaction(async (tx) => …)` (with `tx.query`/`tx.one` on the same connection, and `tx.onCommit(cb)` for side effects that must only happen after COMMIT), `ping()`, and `withPublicId(insert)` (retries on a duplicate random 8-digit `users.public_id`). The schema lives in `db/schema.sql`. It's applied statement by statement at startup; `multipleStatements` stays off. Keep it idempotent (`CREATE TABLE IF NOT EXISTS`) and free of FOREIGN KEYs (PlanetScale compatibility). Changes to tables that already exist go in `MIGRATIONS` in `db.js`: idempotent async steps run after the schema on every startup. They check `information_schema` first (`columnExists`/`indexExists`), and the change must also go in `schema.sql` so fresh installs get it directly. Timestamps are `BIGINT` ms, except `ad_rewards` and `duck_rounds`, which use `DATETIME` because their time checks (cooldowns, 24 h windows) are done with MySQL `NOW()`. Wrap BIGINT values from rows in `Number()` before comparing (`supportBigNumbers` is on).
- `ranks.js` — ranks by total wagered. `TIERS` (8 tiers × 3 divisions, plus "Mito") is the single source of thresholds; `rankOf(wagered)` / `progressOf(wagered)` are pure and unit-tested in `test/ranks.test.js`. An in-memory `wageredCache` lets `badgeOf(userId)` stay synchronous for blackjack seats and chat. It's refreshed from MySQL on every socket connection (`load(id, { fresh: true })`), loaded before sitting or chatting, and updated by `wallet`'s `'wagered'` event. That event makes `server.js` emit `rank` (with `up` when the step rises) to the user's room, and re-broadcast their table if the step changed. `GET /api/leaderboard` (top 10 by credits, cached 5 s; ties broken by id; plus the caller's position) and `GET /api/ranks`. `users.wagered` and the `users_credits` index are added to old databases by `MIGRATIONS` in `db.js`, which backfills wagered from bet/refund ledger rows.
- `transfers.js` — `GET /api/users/:publicId` (look up a recipient), `POST /api/transfer {to, amount}`, `GET /api/transfers`. The actual money move is `wallet.transfer()`: one transaction that debits, credits, writes the `transfers` row and both ledger rows. Its `'sent'` event makes `server.js` emit `transfer:received` to the recipient. The per-user rate limits use `auth.rateLimit({ key })`.
- `ads.js` — rewarded ads (house ads only: files in `public/spots/`, catalog in `src/ads.config.json`, validated at startup; invalid entries are dropped with a warning). `GET /api/ads/status`, `POST /api/ads/start`, `POST /api/ads/claim {token}`, all behind `requireUser` and a shared per-user `auth.rateLimit` (20/min); with `ADS_ENABLED=0` they return 404. `startAd` locks the user row (`SELECT … FOR UPDATE`), returns the existing unclaimed/unexpired row if any (so reloads reuse the token), then checks cooldown and the daily limit (claims in the last 24 h) and inserts a row with a random 32-hex token and `ready_at`/`expires_at` computed with `NOW()`. `claimAd` runs a conditional `UPDATE … SET claimed_at = NOW() WHERE token AND user_id AND claimed_at IS NULL AND NOW() BETWEEN ready_at AND expires_at`, and only if it affected one row it calls `wallet.credit(…, tx)` in the same transaction; otherwise it maps the row state to 404/409/425 (`retryAfter`)/410. Its `'claimed'` event makes `server.js` emit `ads:claimed` to the user's tabs. Ad selection lives behind `pickAd()`/`describeAd()` so a third-party provider can replace it without touching `startAd`/`claimAd`. `public/spots/` is excluded from the asset hash. Client-side names deliberately avoid "ad"/"ads" (script `js/rewards.js`, `window.RewardsUI`, ids/classes `rw-*`, media in `/spots/`) because ad blockers' cosmetic and URL filters (EasyList `###ad-wrap`, `##.ad-btn`, `.org/ads/`…) would hide or block them; keep new names that way.
- `ducks.js` — free single-player duck game. Active rounds live in memory (`Map` userId → `DuckRound`), one per user; every user operation and every round timer goes through that user's `SerialQueue` (timers via `schedule()` → `queue.fire()`, and they no-op once `round.ended`). `DuckRound` is the pure state machine (no DB/timers; unit-tested): ducks are generated from an HMAC of the round's random `seed`; `startWave()` fixes each duck's `spawnAt`/`escapeAt`; `shoot(x, y, t, serverT)` rejects `|t − serverT| > 500 ms` or out-of-order `t` without spending ammo, ignores shots with no ammo, then hits at most the nearest flying duck of the current wave with `t ≥ spawnAt + 250` and `t < escapeAt` using `duckPosition()`. Running out of ammo makes the wave's remaining ducks escape. Ducks are emitted one at a time with `ducks:spawn` when they appear (never ahead of time); a duck is only marked escaped `LATENCY_MS` after `escapeAt`, so a slightly late shot can still count. The round ends when the last wave resolves, on `ducks:quit`, after 60 s without shots, or 30 s after the user's last socket disconnects (`setOnline()`, called by `server.js`). `end()` → `settle()`: one transaction that locks the user row, recomputes the remaining daily quota (`SUM(reward)` of rounds with `credited_at` in the last 24 h), runs `UPDATE duck_rounds … WHERE id AND user_id AND credited_at IS NULL`, and only if it affected one row calls `wallet.credit(…, tx)`. `init()` closes rounds left open by a restart without paying them. `GET /api/ducks/status` (`{ enabled, reward, ducksPerRound, dailyLimit, dailyRemaining, cooldownSeconds, resetSeconds, active }`). Speeds, radius, timings and the 10 shots/s per-user limit are constants at the top of the file.
- `trivia.js` (+ `trivia-questions.js`, the bank: per category, `[question, correct, wrong, wrong, wrong]`; the server shuffles options with `crypto`) — single-player trivia. `trivia:start {amount}` (10–100 000) inserts the `trivia_rounds` row and calls `wallet.bet(…, tx)` in one transaction, so an insufficient balance leaves nothing behind. One active round per user in memory (`Map` userId → `TriviaRound`); every operation and the round's single timer (`setTimer()`, which replaces the previous one) go through that user's `SerialQueue` and no-op once `round.ended`. `TriviaRound` is the pure state machine (unit-tested): `ready → spinning (SPIN_MS) → question (ANSWER_MS) → answered → spinning … → finished` after `QUESTIONS` (5). The server picks the category with `crypto.randomInt` and the question with `pickQuestion()` (no repeats within a round; avoids the user's last 60 if possible). `snapshot()` never contains the question while spinning, nor `correctIndex` until answered. An answer later than `deadline + GRACE_MS`, or no answer (timer), counts as wrong. In `ready`/`answered` the wheel spins by itself after `IDLE_MS`, so abandoned rounds always finish. `finish()` → `settle()`: conditional `UPDATE trivia_rounds … WHERE status = 'playing'`, then `wallet.credit(…, tx)` with `payoutFor(bet, correct)` (`MULTIPLIERS`: 5→×3, 4→×2, 3→×1.5, floored; else 0). `init()` refunds rounds left `playing` by a restart (`refundBet(…, tx)`, status `refunded`). Ledger reasons `trivia:bet|win|refund:<roundId>`.
- `public/js/duck-path.js` — the trajectory, as an ESM module shared by server and browser: `duckPosition(params, t)` (straight flight bouncing off the sides/top — spending `bounces` — and always off the grass line; once out of bounces the duck flies off-screen), `duckEscapeAt()`, `distance()` (16:9-corrected, in screen heights). Only `+ − × ÷` and `Math.sqrt`, so every JS engine gets bit-identical results; the server precomputes `vx`/`vy` with sin/cos. `ducks.js` loads it with `import()`; `public/js/package.json` (`"type": "module"`) is only there so Node doesn't warn about it.
- `chat.js` — channels are the Socket.IO room names (`roulette`, `bj:<id>`). `server.js` only accepts `chat:send` for `roulette` or a `bj:` room the socket is currently in. Text is stripped of control characters and capped at 300 chars; each user gets 5 messages per 8 s. History (last 50) is sent as `chat:history` on connect (roulette) and on `bj:watch` (table).
- Blackjack cameras and voice chat (WebRTC). Each seat has `media: { socket, video, audio, rev }` (the socket that publishes). It's exposed in `bj:state` as `media: { peer, video, audio, rev }`, set via `bj:media {video, audio}` → `table.setMedia()` (which bumps `rev` on every change), and cleared on disconnect (`clearMedia`) and when the seat is freed. Viewers key connections by `peer#rev`, so any camera/mic toggle makes them reconnect with the new tracks. Media never touches the server. `server.js` only relays `rtc:signal` (`want`/`offer`/`answer`/`candidate`/`bye`) between a publisher and a socket watching that publisher's table (`rtcTableFor`). The relay has its own rate limit (60/s), strips unknown fields (`cleanSignal`), and doesn't go through `on()`. `rtc:gone` tells publishers that a viewer left. ICE servers come from `RTC_ICE_SERVERS` (JSON, default Google STUN), sent as `rtc:config`. `Permissions-Policy` allows `camera=(self)` and `microphone=(self)` only.
- Account limits (`auth.js`): registration runs in a `SerialQueue`. It checks the `registrations` table against `ACCOUNTS_PER_DEVICE` (the `ksdev` httpOnly cookie, set by `deviceId()` on register/login) and against `ACCOUNTS_PER_IP` within `ACCOUNTS_IP_WINDOW_HOURS`, then inserts the user and its registration row. Device and IP are stored only as HMACs keyed with the JWT secret (`fingerprint()`). `clientIp(req)` reads `CLIENT_IP_HEADER` (default `cf-connecting-ip`, because production is behind Cloudflare, so `req.ip` is the proxy), and it's also the default key for `rateLimit`. Set both limits to 0 for local testing.
- `roulette.js` — `RouletteGame` (built with `await RouletteGame.create(io)`, which loads the history): one global shared round loop driven by timers (`betting` 20 s → `spinning` 7 s → `result` 5 s). Bets are debited immediately on placement and held in memory (`Map` userId → Map of spots); `settle()` pays winners. Bet types are declared in the `BET_TYPES` table (`payout` = profit per credit; stake is returned on top). Only the last 30 spins are persisted.
- `blackjack.js` — `BlackjackTable`: one 15-seat table (seat count is a constructor option). `server.js` creates `BLACKJACK_TABLES` (5) of them in a `Map` keyed by id 1–5. A user may sit at only one table at a time (`tableOf(userId)`), so `bj:bet`/`bj:action`/`bj:leave` resolve the table from the seat and take no table id. Each table's `broadcast()` calls `onChange`, which drives a debounced `bj:lobby` summary sent to everyone. `settle()` also emits a private `bj:outcome` to each player so the win animation fires even when they're watching another table. Dealing speeds up with many players (`DEAL_TOTAL_MS`). State machine: `waiting → betting → dealing → playing → dealer → settled → waiting`. All progression is timer-driven through `schedule()`/`clearSchedule()` (a single `this.timer`), with `broadcast()` after each step so cards are dealt one at a time. `advance()` finds the next unfinished hand and sets a turn timeout (auto-stand). Leaving mid-hand marks the seat `leaving` and frees it at `resetRound()`; leaving before cards are dealt refunds the bet.

All game state other than what's in MySQL (balances, ledger, avatars, chat, transfers, roulette history) lives in memory and is lost on restart. In-flight bets that were already debited are not refunded on a crash. If a payout fails at settle time, it is logged (`No se pudo pagar…`) and the round continues.

### Socket protocol
- Client → server (with ack callback): `bj:media {video, audio}`, `roulette:bet {type, value, amount}`, `roulette:clear`, `chat:send {channel, text}`, `bj:watch {table}` (switch the watched table; the socket joins only that table's room), `bj:sit {table, seat}`, `bj:leave`, `bj:bet {amount}`, `bj:action {action: hit|stand|double|split}`, `ducks:start`, `ducks:shot {roundId, x, y, t}`, `ducks:quit {roundId}`, `ducks:resume` (replies with `ducks:round` to that socket only: the active round's snapshot, or `null`; never starts one), `trivia:start {amount}`, `trivia:spin {roundId}`, `trivia:answer {roundId, choice: 0-3}`, `trivia:resume` (replies `trivia:round` to that socket: snapshot or `null`).
- Trivia events go to `user:<id>`: `trivia:round` (full snapshot after every change, with `endsIn`/`duration`), `trivia:end {bet, correct, total, multiplier, payout, error}`. `trivia:config {min, max, questions, multipliers, categories, answerMs}` is sent on connect.
- Duck events go to `user:<id>` so every tab stays in sync: `ducks:round` (snapshot, only already-spawned ducks), `ducks:wave`, `ducks:spawn {duckId, params}`, `ducks:shotResult {t, hit, duckId, ammoLeft, ignored}`, `ducks:escaped {duckId, at}`, `ducks:end {ducksHit, reward, dailyRemaining, cooldownSeconds, resetSeconds, balance, error}`. Most carry `now` (server round time in ms) so the client can keep its round clock in sync.
- Server → client: `balance`, `profile` ({ avatar }), `roulette:state`, `roulette:bets`, `roulette:outcome`, `bj:state` (includes the table `id`/`name`; the client ignores states from tables it isn't watching), `bj:lobby` (per-table `{id, name, seats, occupants, phase}`), `bj:outcome` (private), `chat:history`, `chat:message`, `transfer:received`, `ads:claimed`, `rtc:config`, `rtc:signal`, `rtc:gone`. `rtc:signal` also goes client → server with no ack. State events carry the full public snapshot (not diffs), including `endsIn` and `duration` (ms of the current timed phase) for countdowns and progress bars.
- Rooms: `user:<id>`, `roulette`, `bj:<tableId>`. Sockets join a `bj:` room only through `bj:watch`/`bj:sit`, and the client re-sends `bj:watch` on every (re)connect.

### Client (`public/`)
Production sits behind Cloudflare, which lets browsers cache `.css`/`.js` for 4 h. To stop old assets from being paired with a new `index.html` after a deploy, `server.js` serves `index.html` itself (`Cache-Control: no-cache`). At startup it appends `?v=<hash of public/ + dependency versions>` to every `/css`, `/js` and `/vendor` URL. New assets referenced from `index.html` must use those path prefixes to be versioned.

Client libraries (Bootstrap, Bootstrap Icons, `@fontsource` Inter/Cinzel, `canvas-confetti`) are npm dependencies served by `server.js` under `/vendor/...` from `node_modules`. The CSP only allows `'self'`, so never link a CDN; add a package and a `/vendor` route instead. `canvas-confetti` must be created with `useWorker: false`, because the CSP blocks blob workers.

Plain scripts load in order in `index.html`. `roulette.js` and `blackjack.js` define the globals `window.RouletteUI` / `window.BlackjackUI` (IIFE modules exposing `init(ctx)`). Then `app.js` handles auth, tabs and the socket, and calls both `init`s with a shared `ctx`: `socket`, `emit` (promise wrapper with a 5 s timeout), `toast` (Bootstrap Toasts), `celebrate({ amount, net, detail, big })` (queued centre-screen win announcement: "¡Ganaste!" when net > 0, "¡Acertaste!" otherwise; confetti only when net > 0), `avatar(name, url)` (photo, or the initial on a per-name hue), `api` (errors carry `status` and the JSON body as `data`), `confetti()`, `credits()`, `chat` (`ChatUI.setChannel`), `transfer` (`TransferUI.open(publicId)`), `renderChips`, `reducedMotion`, `user`. `chat.js` (floating chat), `transfer.js` (send-credits modal), `rewards.js` (`RewardsUI`, initialised with `?.` so the app still works if it's blocked: the "+100" button and the rewarded-ad modal; its countdown pauses while the tab is hidden, is UX only, and the token is kept in memory only) and `media.js` (`MediaUI`: camera + voice) and `ranks.js` (`RankUI`: SVG rank emblems via `emblem(rank, size)`, the Ranking tab polled only while active, and the rank-up announcement through `celebrate({ badge })`) are the other client modules. In `MediaUI`, the publisher answers each viewer's `want` with an offer, and viewers call `sync(state)` after every blackjack render. `<video>` elements persist per user and are always muted; sound plays through per-user `<audio>` elements inside the hidden `#bj-audio`, which never moves. A shared `AudioContext` with one `AnalyserNode` per stream toggles `.speaking` on `.seat[data-user]`. Video is shown only once real frames arrive (`videoWidth > 16`). the chat channel follows the active tab and, in blackjack, the watched table. Roulette calls `celebrate` whenever the payout is > 0, and blackjack whenever one of your hands wins.

- `ducks.js` (`DucksUI`, `init(ctx)` + `setActive(bool)` from the tab switcher) loads `duck-path.js` with `import()` using its own `?v=` so both files come from the same deploy. The "Patos" tab stays hidden unless `/api/ducks/status` says it's enabled; on (re)connect it sends `ducks:resume` and, on the first page load, switches to the tab if a round is in progress. The round clock is `performance.now() − clockStart`, where `clockStart` is the minimum of `performance.now() − now` over server messages, so the `t` it sends is never ahead of the server. Canvas: 16:9 with normalized coordinates, DPR capped at 2, pre-rendered back (sky, hills, lake) and front (reeds, grass) layers with the ducks drawn in between, and the rAF loop stops when nothing moves. A duck only falls on `ducks:shotResult` with `hit: true`; before that the client only draws a provisional flash. Optimistic ammo is reconciled as `ammoLeft − pending shots`. All art is drawn in canvas and all sounds are synthesized with Web Audio (mute saved in `localStorage`).
- `trivia.js` (`TriviaUI`) renders everything from the `trivia:round` snapshot. The category wheel is a CSS `conic-gradient` div rotated with a `transform` transition (`spinTo()`, cumulative `wheelAngle`); colours/icons per category are in `LOOK`, names/order come from `trivia:config`. `#trivia[data-phase]` drives CSS: on screens < 992 px the wheel is hidden outside `ready`/`spinning`, so the question stays above the fold (`spinTo()` forces a style flush because the wheel may have just become visible). The summary appears `REVEAL_MS` after `trivia:end`, and `celebrate` fires when the payout is > 0. `renderChips(container, onPick, selectable, min)` hides chips below `min`. Chip labels use `ctx.short()` (1K, 25K, 100K) from `CHIP_VALUES` in `app.js`.
- The roulette wheel is a `<canvas>` with two pre-rendered layers (static bowl, rotating disc) redrawn every frame by a `requestAnimationFrame` loop. The wheel idles slowly. During a spin the ball's path is computed so it lands in the server-chosen pocket (`startSpin`/`ballDuringSpin`).
- Blackjack keeps persistent per-hand card containers (`cardWraps`), so only newly dealt or flipped cards animate when a full snapshot arrives. Per-render animations go through `animQueue`/`runAnimations`. Seat elements are cached in `seatCache`, keyed by a JSON of everything the seat displays. Only seats whose key changes are rebuilt and swapped in place, so the other seats' DOM, images and videos are untouched. If `seatEl()` starts depending on new state, add it to that key.
- Performance rules (the page is meant to stay smooth on weak devices; keep visuals identical when changing these): no `background-attachment: fixed` (the page background is a fixed `body::before` layer); no `backdrop-filter` except the sticky topbar and the login card; animate `opacity`/`transform` only (pulsing glows are `::after` layers fading their opacity, never animated `box-shadow`); no CSS `filter` on the constantly redrawn wheel canvas; no per-frame `shadowBlur` (the winning-pocket glow is pre-rendered in `glowFor()`). Versioned `/css`, `/js` and `/vendor` URLs (`?v=`) are served `immutable` for a year.
- The theme lives in `css/style.css` and overrides Bootstrap's `--bs-*` variables (`data-bs-theme="dark"`). Playing cards use `.pcard` and compact hands use `.compact`, because Bootstrap already defines `.card` and `.small`. Animations respect `prefers-reduced-motion`.

Game constants (limits, timings, rules) live at the top of each server game module; the client receives limits via the state payload, but some rules are duplicated client-side for display (e.g. `RED` numbers, `rankValue`), so update both sides together.
